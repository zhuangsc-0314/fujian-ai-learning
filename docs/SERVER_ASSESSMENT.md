## 结论

适合继续作为项目的开发测试与小范围朋友试用候选服务器；当前状态尚不能认定满足多人正式上线条件。采用外部聊天/Embedding服务、一个API进程、单Worker、小批次处理、独立项目数据与网络，完成HTTPS、权限、备份及压测后再接受朋友试用。

不建议在保留全部现有业务时直接叠加完整AI基础设施、本地PyTorch Embedding、OCR、浏览器抓取或本地大语言模型。主要约束是内存和磁盘余量，不是当前CPU负载。先不要求购买新机器；长期多项目共存且资源测试失败时再评估8GB内存、80GB或以上存储。配置建议不是容量承诺。

## 针对本机的部署方案

- 前端在本机电脑/CI构建，服务器只提供静态文件；避免上线时在小内存机器进行Node构建。
- 一个Caddy入口负责HTTPS与/api；API一进程起步。
- Worker并发1，Redis仅作为本项目任务队列，状态落PostgreSQL。
- 聊天API沿用DeepSeek候选；Embedding改为服务化方案优先，供应商与预算在RAG阶段确认。保留原AI适配边界。
- 本项目采用独立受支持PostgreSQL/pgvector实例或托管实例，不直接升级或改动现有其他项目数据库。新实例只容器内网可见。
- 文件使用私有对象存储，备份异机；不要把同一40GB系统盘上的备份当作灾备。
- Compose项目名、网络、数据卷、应用账号、密钥、域名分别隔离；共享宿主机仍共用资源和故障域，容器不等于独立服务器。
- 初始内存预算示例：API256–384MiB、Worker256–512MiB、PostgreSQL384–512MiB、Redis64–128MiB、入口32–96MiB，总计约1.0–1.6GiB。这是待测预算，不是已测占用；进程、数据库配置、容器硬限制要结合OOM测试，不能只写限制值。
- 保留至少约0.5GiB可用内存作为试用目标；内存持续下降或持续换页时停止增加并发并调整部署。
- 系统盘建议试部署前达到约15–20GB可用（工作目标），通过确认后的缓存清理/数据外移/扩容达成；镜像更新、回滚镜像和日志均需空间。日志轮转并设磁盘告警。

PostgreSQL14官方计划2026-11-12结束支持。新项目主推荐独立PostgreSQL17与兼容pgvector，并锁定镜像版本；具体镜像/扩展版本在部署时验证。既有14.24不在本轮升级。[PostgreSQL维护策略](https://www.postgresql.org/support/versioning/)

## 上线前必须完成

1. 数据库网络：当前3306/5432从本机经公网可达。核对是否有明确的远程访问需要；收窄到必要来源/私网或SSH隧道，不盲目关闭导致其他项目中断。
2. HTTPS：确认域名和云端80/443规则，配置证书和同源入口；数据库与Redis不对公网暴露。
3. 运维身份：SSH根账户只用于必要运维；应用进程与数据库使用独立低权限身份，秘密不入Git/前端/日志。
4. 资源与磁盘：为新项目设置并发、限额、日志轮转；对现有缓存制定可审阅清理清单后再执行，本次没有清理。
5. 数据归属：完成双账号的材料、文件、向量、会话、错题、任务和工具隔离测试，包括撤销共享后的派生回答。
6. 备份恢复：数据库与源文件异机备份；恢复到独立位置核验，不覆盖现有业务；验证回滚。
7. 压测：2–5用户读取/作答，加1–2个AI任务、1个解析任务，记录p95、队列等待、available内存、si/so、磁盘/数据库表现及对既有业务影响。
8. 预算：按任务token预留和结算；401网络测试不证明API Key有效或额度充足。
